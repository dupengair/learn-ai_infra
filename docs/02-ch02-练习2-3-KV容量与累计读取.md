# 练习 2-3 分析：输出变长后，KV 容量与累计读取量如何增长

## 2. 数值的产生链路

```
calc.py reproduce → reproduce.run()
  └─ for row in scenarios['cache_sequence']:            # reproduce.py:1070
        cache_sequence.calculate(**row)                  # batch/prompt/steps/prefix_hit/element_bytes
        save(row['id'], result)                          # → results/cache-sequence-qwen3-8b-b1.json
```

`cache_sequence.calculate()`（111 行，纯标准库）只读官方 config（`configs/models/qwen3-8b/config.json`，本仓库完好，02-02 已验证可过哈希校验），**不碰任何 LFS 指针文件**——所以练习的两组数字都可以现场复算，且 G=1025 与已复算文件已核对**逐位一致**。

关键代码（:49-51，本练习的心脏）：

```python
# Before each append: P, P+1, ..., P+G-1. The current token is separate.
history_records = steps * prompt + steps * (steps - 1) // 2   # = n_d·H + n_d(n_d−1)/2
visible_pairs = history_records + steps                        # 注意力可见对另加每步当前 token
```

每个 variant 的账（:64-70）：`unit = batch × history_bytes_per_token` 后，

- `final_persistent_state_bytes = (prompt+steps) × unit`
- `decode_prior_history_read_payload_bytes = history_records × unit`（旧上下文累计读取）
- `decode_append_write_bytes = steps × unit`（decode 新增写入）

## 3. 练习解答（全部已用代码逐位验证）

每 token KV：c_KV = 2×36×8×128×2 B = 147,456 B（144 KiB）。S=0 ⇒ H=P=8192。

| 量 | G=513（n_d=512） | G=1025（n_d=1024） | 比例 |
| --- | ---: | ---: | ---: |
| 后续 decode 次数 | 512 | 1024 | ×2 |
| 累计读取 token 次数（n_d·H+n_d(n_d−1)/2） | 4,325,120 | 8,912,384 | ×2.0606 |
| **累计旧上下文读取量 R_old** | 637,764,894,720 B ≈ **594.0 GiB** | 1,314,184,495,104 B ≈ **1223.9 GiB** | ×2.0606 |
| 生成阶段（decode）新增 KV | 75,497,472 B = 72 MiB | 150,994,944 B = 144 MiB | **×2.000** |
| **最终 KV 总容量** | 8704×147,456 = 1,283,457,024 B ≈ **1.1953 GiB** | 9216×147,456 = 1,358,954,496 B ≈ **1.2656 GiB** | **×1.0588** |

（G=1025 列与 `cache-sequence-qwen3-8b-b1.json` 逐位一致；G=513 列由 `calculate(steps=512)` 现场复算，手工公式交叉验证一致。）

**为何三个比例各不相同**——把 R_old 拆开看就明白了：

1. **新增 KV 严格 ×2**：c_KV·n_d 是 n_d 的线性函数，decode 翻倍新增就翻倍。
2. **最终容量只 +5.9%**：c_KV·(H+n_d) 中 prefill 基座 H=8192 不随输出变，n_d 从 512 涨到 1024 只把总量从 8704 推到 9216（9216/8704=1.0588）。输出相对输入越短，总容量越接近"只由输入决定"。
3. **累计读取 ×2.06，略超翻倍**：R_old 的矩形项 n_d·H 严格 ×2（4,194,304→8,388,608），但三角形项 n_d(n_d−1)/2 是 n_d 的二次函数，×4.0039（130,816→523,776）。加权结果 2.0606。三角形项是"生成期新加的 token 也互相读"——正是正文 F_decode,total 公式里 a·n_d(n_d−1)/2 那一项的 KV 读取面。

一句话：**容量看终点（线性、被 H 主导），读取看路径（每步都重读全部历史，含二次项）**。这就是例题 2-3"累计读取是最终存储的近千倍"（1223.9/1.2656 ≈ 967×）的机制。

**KV 位宽减半（element_bytes 2→1，c_KV=73,728 B）**：实测三项缩放比分别为 **0.5000 / 0.5000 / 0.5000——三项全部减半**。因为三项都是 `unit = batch×history_bytes_per_token` 的线性函数（:61,66,67,70），位宽直接除进 c_KV。不变的是：权重容量（15.26 GiB）、矩阵 FLOPs、以及累计读取"次数"（8,912,384 是 token 计数，与字节无关）——减半的是每次读取的**载荷**。代码里这个旋钮就是 `calculate(..., element_bytes=1)`。

## 4. 相关但不同的两件事

- **`qwen3.generation()`**（`models/qwen3.py:243-268`）：同一求和公式的另一实现（`kv_existing_history_read_bytes = batch×per_token×(steps×history + steps×(steps−1)//2)`），走 forward 命令族，还可给每步矩阵 FLOPs 求和。练习 2-3 的账在 `cache_sequence` 里（已复算文件即其产物），但两者可互为验算。
- **prefix_hit=6144**：同一文件里还有前缀命中账（`saved_prefill_pairs_per_request` 等），那是练习 2-2 第 3 问的延续，本练习 S=0 用不到。
