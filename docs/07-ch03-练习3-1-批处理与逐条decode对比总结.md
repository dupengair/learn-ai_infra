# 批处理与逐条 Decode 的对比总结：资源、优势与代价

> 本文汇总实验 03-01、练习 3-1（含追问两则）、练习 2-2/2-6 的数据，回答一个问题：**batch 批处理与逐条（B=1）decode 在资源消耗和计算量上到底差在哪，优势的边界在哪里**。全部数字来自前面已逐位验证的实验产物。

## 1. 核心事实：五项资源对 batch 的响应各不相同

以实验 03-01 时段 A（Qwen3-8B，prompt 4096＋输出 128）为基准，batch 从 1 → 8 → 32：

| 资源项 | B=1 | B=8 | B=32 | 随 B 的规律 |
| --- | ---: | ---: | ---: | --- |
| decode 矩阵计算量 | 2.252 TF | 18.01 TF | 72.05 TF | **线性 ×B** |
| decode 权重读取（整段） | 1,804.4 GiB | 1,804.5 GiB | 1,804.5 GiB | **完全不变**（每步 14.10 GiB × 128 步） |
| decode 历史读取 | 73.1 GiB | 584.9 GiB | 2,339.7 GiB | **线性 ×B**（各读各的 KV） |
| 结束时常驻 KV | 0.580 GiB | 4.641 GiB | 18.562 GiB | **线性 ×B** |
| prefill 权重读取（合并批） | 14.13 GiB | 14.35 GiB | 15.10 GiB | **几乎不变**（一次读取服务 B×P 行） |

练习 3-1 的同一现象（同步生成 1,024 个总输出 token）：

| 量 | 逐条：1 条 × 1024 输出 | 批处理：8 条 × 128 输出 |
| --- | ---: | ---: |
| decode 调用轮数 | 1,023 轮 | 127 轮 |
| decode 权重读取 | 14,421.5 GiB | 1,790.4 GiB（**÷8.06**） |
| 每轮服务的 token | 1 个 | 8 个（算术强度 ×8） |

**规律的本质是共享性差异**：权重是全批**只读共享**的（一次读入供所有请求的乘加复用，第 2 章"同一份权重参与更多行"），所以不随 B 变；KV 是**每请求私有的**（请求间上下文独立，不能共享），所以两项（读取与容量）都严格线性。计算量则每 token 都是刚性的，自然线性。

## 2. 批处理的优势

1. **每 token 的权重带宽成本 ÷B**——decode 的主导开销从"每 token 读一遍 14 GiB 权重"变成"B 个 token 合读一遍"。带宽受限段（小 B）里，吞吐近似 ×B 提升：练习 3-1 用 1/8 的权重读取量完成相同总输出。
2. **算术强度 ×B，把 decode 从带宽区推向算力区**——B=1 的 decode 是矩阵×向量（GEMV），每读 1 字节权重只做少量乘加；B=32 时同一份权重服务 32 行，FLOPs/字节提高 32 倍，tensor core 利用率随之上升。这是"decode 受带宽限制"表述的完整版：**只在 B 小的时候成立**。
3. **矩阵形状变大，硬件效率提高**——prefill 合并批尤其明显：8 条各 1024 行合并成 8,192 行的大 GEMM，权重读取 14.11→14.16 GiB 几乎不变（练习 3-1 验证），计算量 8 倍却落在高效率区间。
4. **MoE 场景的专家并集次线性增长**——练习 2-6：B=1 时只点亮 8/256 个专家（读 1.875 GiB），B=64 全点亮（60 GiB）。专家权重读取随并集（sublinear）而非随 B 线性增长，batch 越大每 token 分摊的专家权重越少，直至并集触顶。

## 3. 批处理的代价与边界

1. **KV 容量线性膨胀——显存墙**。B×H×144 KiB：练习 2-2 的极端例是 batch=64、历史 8192 时 KV 达 **72 GiB**（权重才 15.3 GiB）。容量先于带宽成为硬约束：batch 上限常常不是带宽算出来的，是显存装不下。
2. **KV 历史读取线性增长——带宽瓶颈转移**。追问二的交点公式 B\* = R_W/(c_KV·H)：H=1024 时 B=101、H=8192 时 B=13、H=131072 时 **B=1 即超**。越过 B\* 后再加 batch：权重侧一点不省，KV 侧线性变重——**长上下文的 decode 加批反而恶化带宽**。这就是"上下文越长，批内权重复用的收益越早受到限制"（例题 2-2）。
3. **计算量线性增长，延迟换吞吐**。批内 32 条共享一步 decode：吞吐 ×32，但每条请求的单步延迟不低于 B=1 时（算力段甚至更差）。对 ITL（token 间延迟）敏感的交互场景，大 batch 直接伤害体验。
4. **同步假设与气泡**。练习 3-1 的"8 条同步生成"要求输出等长；实际输出长度随机，先完成的请求留下空槽（气泡），总步数由最长者决定。连续批处理（第 8 章）动态填补气泡，但引入调度开销与实现复杂度。
5. **排队与尾延迟**。凑批要等待（TTFT 上升），不凑批则带宽浪费——批处理把"什么时候执行"的问题从单请求尺度搬到调度器尺度，p99 尾延迟的管理变难（实验 3-2 的排队主题）。

## 4. 资源视角与吞吐视角：batch 到底"换"到了什么

"batch 换的是权重读取"与"batch 用吞吐换速度"两种说法需要辨析——前者是**机制**，后者是**效果且方向说反了**：

1. **batch 不加速单条请求**。decode 的生成是串行依赖链（下一个 token 依赖上一个 token 的输出，练习 2-1 已证明这条链无并行可挖）；批内每条请求的单步延迟不降反升（算力段更差）。单条请求每 token 的时间下界由依赖链和该步访存决定，batch 改变不了它。
2. **吞吐 ×B 的物理来源正是权重共享**。decode 处于带宽区：每步时间 ≈ 权重读取时间（14.10 GiB ÷ 带宽）。批内 B 条并行时每步时间几乎不变（还是那 14.10 GiB，外加 B×c_KV×H 的 KV），但每步**产出 B 个 token** ⇒ 吞吐 ×B。如果权重不共享（B 条各自独立读一遍），batch 对吞吐毫无帮助——**不是"并行计算加速了生成"，而是"同一次访存服务了更多 token"**。
3. **roofline 验证**（Qwen3-8B，H=1024，实测）：每步算术强度 B=1 时 1.04 FLOP/B，B=8 时 8.32，B=32 时 33.3——都远低于 H100 BF16 平衡点 ≈295 FLOP/B，即整个区间仍在带宽区；而带宽区吞吐 = 带宽 × 强度，强度 ×B ⇒ 吞吐 ×B。直到强度逼近平衡点（B~280）才开始进入算力区、吞吐增长放缓。
4. 所以准确的交易结构是：**用单条请求的延迟（持平或变差）和 KV 的两个线性项，换系统的吞吐；吞吐的来源是每 token 权重带宽成本从 R_W 降到 R_W/B**。"换权重读取"与"换吞吐"是同一笔交易的因果两面——资源账是因，吞吐是果。

## 5. 追问两则：batch 里的依赖去哪了；小模型还值得批处理吗

**追问一：decode 是串行依赖链，批内并行的到底是什么？**

依赖链有两条，不能混淆：

- **请求内（时序）依赖**：同一条请求第 t+1 个 token 依赖第 t 个的输出——这条链决定一条请求内部必须逐步串行，**batch 不触碰它**（批内每条请求照样走自己的 G−1 步）；
- **请求间依赖**：**不存在**。请求 A 的第 5 个 token 与请求 B 的第 30 个 token 没有任何数据依赖，只是被调度器对齐到同一物理时刻、合并成一次前向调用。

代码形状直接可见：decode `Scenario(batch=8, history=1024, tokens=1)` 的 `qk` 算子是 `Q: [8,32,1,128]`、`K_shared: [8,8,1025,128]`——第一维 b=8 是 8 条**独立请求各查各的** 1025 条 KV，注意力计算在 batch 维上互不交互。所以"批内并行"的准确含义是：**不同请求的串行链对齐到同一时间步，共享该步的权重读取**；每条链的长度（步数、延迟）一点没变。特别注意：不能把一条请求的输出拆开并行生成——练习 3-1 情况二是"本来就有 8 条独立请求"，不是"把 1 条切成 8 段"。唯一的例外是投机解码（第 8 章）：草稿模型先猜一串、目标模型一次前向并行**验证**多个候选——那是并行验证，不是并行生成。

**追问二：小模型（如 0.6B）上下文一长，KV 很快压过权重，batch 不就不划算了？——完全正确，这正是 B\* 公式的推论。**

$$B_*=\frac{R_W}{c_{\mathrm{KV}}H}$$

模型变小，R_W 缩小的速度远快于 c_KV（权重 ∝ 参数量，KV 只 ∝ 层数×KV 头×head_dim）。以 Qwen3 家族公开配置手算（0.6B：28 层、8 KV 头、head_dim 128 ⇒ c_KV=114,688 B/token，BF16 权重 ≈1.2 GB）：

| 模型 | 每步权重读 R_W | c_KV | B\*（H=1024） | B\*（H=8192） |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-8B | 15.14 GB | 147,456 B | 101 | 13 |
| Qwen3-0.6B | ≈1.2 GB | 114,688 B | **11** | **1.3** |

0.6B 的 B\* 比 8B 小一个数量级（权重差 ~12.6 倍，c_KV 只差 1.29 倍）：**H=1024 时 batch 加到 11、KV 读取就压过权重；H=8192 时几乎 B=1 就持平**。两点实践印证与一个对称面：

1. 这就是端侧小模型普遍配更激进 KV 压缩（KV 头更少/滑窗/量化 KV）的结构性原因——它们的带宽瓶颈天生在 KV 不在权重；
2. 大模型反而更能承受 batch（B\* 大），批处理收益区间更宽；
3. 对称的另一面：小模型 B=1 时每 token 权重读取本来就小（1.2 GB vs 15.1 GB），"不批处理造成的浪费"也小——**B\* 小 ≠ 灾难，只是 batch 的收益区间窄、更早需要靠压 c_KV（而非加 B）来提升效率**。

**批处理是"用两个线性项（KV 容量、KV 读取）换一个常数项（权重读取）的交易**：小 B 时收益近乎线性（每 token 权重成本 ÷B、算术强度 ×B），被 KV 的两个线性项和显存容量先后封顶；最优 batch 大小由三个量共同决定——硬件带宽/算力比（roofline 位置）、上下文长度（B\* = R_W/(c_KV·H)）、以及显存能装下多少 KV。这也解释了后续章节的全部动机：GQA/MLA/压缩 KV（第 2 章）压低 c_KV 从而推高 B\*、P/D 分离让 prefill 与 decode 各自落在合适的 batch 区间（第 8/9 章）、连续批处理用调度填补气泡（第 8 章）。
