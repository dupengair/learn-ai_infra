# 练习 3-1 分析：相同输出总量下，请求数量如何改变模型调用次数

> 练习 3-1〔延伸〕：一条请求输出 1024 token vs 八条请求各输出 128 token，输入均为 1024。求两种情况的 prefill 次数、后续 decode 总步数、各请求结束时的上下文长度；八条同步生成时比较每批共享一次权重的读取轮数；解释总输出相同为何不足以判断完成时间。
>
> 正文对应 `manuscripts/03-推理与训练负载.md` 3.1.1（调用链 = 1 次 prefill + G−1 次 decode，图 3-1）。

## 0. 实验与练习的对应关系

`experiments/ch03/03-01/`（"Prefill 与 Decode 的资源变化"）与练习 3-1 **主题相同但设定不同**：实验比较"时段 A（prompt 4096＋输出 128）vs 时段 B（prompt 512＋输出 3712）"——保持每请求总 4,224 token 只改阶段组成；练习比较"1 条长输出 vs 8 条短输出"——保持总输出 1,024 token 只改请求数。两者是同一论断的两个变体：**总量相同 ≠ 资源/时间相同**。

实验用 CLI 现场生成（`calc.py forward|generate`），**本地完整跑通（exit=0）**——两个命令都只读 Qwen3-8B config。练习 3-1 的场景同样可以用这两个命令现场复算（下文全部验证）。

## 2. 练习解答（全部已用代码逐位验证）

### 调用链与上下文（前两问）

| 量 | 情况一：1 条，G=1024 | 情况二：8 条，各 G=128 |
| --- | ---: | ---: |
| prefill 次数 | **1** | **8**（可合并为一批：一次 `forward --batch 8`） |
| 每条请求 decode 步数 n_d=G−1 | 1023 | 127 |
| decode 总步数 | **1023** | 每条 127；**8 条同步生成时共 127 步**（每步 B=8 并行），串行则 8×127=1016 |
| 各请求结束上下文 S+P+n_d | **2047** | **1151** |
| 最终 KV（Qwen3-8B, 144KiB/token） | 287.9 MiB（2047 token） | 1.265 GiB（8×1151 token） |

### 权重读取轮数（第三问，"每批共享一次权重"）

decode 阶段每一步都要把整份权重读一遍（14.10 GiB），轮数 = 模型调用次数：

| 量 | 情况一 | 情况二（同步） |
| --- | ---: | ---: |
| decode 权重读取轮数 | **1023 轮** | **127 轮**（每轮供 8 条共享） |
| decode 权重读取总量 | 14.10 GiB × 1023 = **14,421.5 GiB** | 14.10 GiB × 127 = **1,790.4 GiB** |
| decode 累计历史读取 | 215.7 GiB | 151.7 GiB |
| prefill 权重读取 | 14.11 GiB（1 次） | 14.16 GiB（合并 1 批；分 8 次亦仅 ~8×14 GiB） |

**读取轮数相差 8.06 倍**（1023/127）——总输出同为 1,024 token，访存量却差近一个数量级。批内共享正是 decode 阶段批处理的全部意义：同一份 14 GiB 权重，情况一每轮只服务 1 个 token，情况二每轮服务 8 个 token，**算术强度（FLOPs/字节）提高 8 倍**。

> **口径辨析：这里的"÷8.06"与实验 03-01 的"完全不变"并不矛盾。** 权重读取总量 = R_W × 轮数，而轮数只由**最长输出长度 G** 决定（同步批走 G−1 步），与 B 无关。两个实验控制的是不同的变量：
>
> | 场景 | 固定什么 | 轮数 | 权重读取总量 | 总 token | 每 token 成本 |
> | --- | --- | ---: | ---: | ---: | ---: |
> | 练习 3-1 情况一（B=1, G=1024） | 总输出 1,024 | 1,023 | 14,422 GiB | 1,024 | 14.08 GiB |
> | 练习 3-1 情况二（B=8, G=128） | 总输出 1,024 | 127 | 1,790 GiB | 1,024 | **1.75 GiB** |
> | 实验 03-01（B=8, G=128） | 每条输出 G=128 | 127 | 1,804 GiB | 1,024 | 1.76 GiB |
> | 实验 03-01（B=32, G=128） | 每条输出 G=128 | 127 | **1,804 GiB（不变）** | 4,096 | **0.44 GiB** |
>
> 实验 03-01 增大 B 时 G 不变 ⇒ 轮数不变 ⇒ **绝对总量不变**（但服务了 B 倍 token，每 token ÷B）；本练习固定总输出、切成 8 条 ⇒ G 缩小 8 倍 ⇒ 轮数 ÷8 ⇒ **总量 ÷8**。一个说的是"总量随 B 不变"，一个说的是"总产出固定时总量随并行度缩短"——同一机制（每步共享一次 R_W）的两个投影。真正普适的表述是**每 token 权重成本 = R_W/B**（B 个 token 合读一遍 14 GiB）。

### 为什么总输出相同不足以判断完成时间（第四问）

完成时间 ≈ Σ(每次模型调用的时间)，而每次调用的时间由**该调用的形状**决定，不只是 token 计数：

1. **调用次数不同**：1,024 次调用（1+1023）vs 135 次（8 prefill 合并 +127 decode）。decode 受带宽限制（每步 14 GiB 权重读取几乎不变而计算很少），轮数直接换算成带宽时间——8 倍轮数差 ≈ 8 倍 decode 带宽时间。
2. **批形状不同**：同为一步 decode，B=1 与 B=8 的矩阵行数差 8 倍。带宽侧两者几乎同价（权重读一次），算力侧差 8 倍——落在 roofline 的哪一段，取决于硬件比值（第 4 章）。
3. **阶段构成不同**：prefill 是大矩阵乘（算力受限、权重读一次摊到 1024/8192 行），decode 是逐 token（带宽受限）。两种调用不可用同一"每 token 时间"折算——实验 03-01 的 B 时段矩阵工作只多 7%，权重读取却多 29 倍，就是这一条的铁证。
4. **同步是理想化假设**：8 条等长才能整齐走 127 步；实际输出长度随机时，批内先完成的请求留下气泡（连续批处理要动态填补，第 8 章）。若 8 条不同步，总步数由最长者决定，还引入调度问题。
5. **到达与排队不在内**：练习只比较"执行已到达的请求"，完成时间还受到达顺序影响（实验 3-2 的排队主题）。

一句话：token 总数只约束了**计算量的数量级**；完成时间由"这些 token 被切分成多少次调用、每次调用什么形状、批内能共享什么"决定——这正是正文"仅把总 token 数相加，会丢失这些 token 分别属于哪个阶段、何时能够执行的信息"的展开。

### 追问一：结束上下文为何是 2047，不是 2048？

把调用链逐步列开（情况一，P=1024，G=1024）：

| 步骤 | 写入 KV 的 token | 产出的 token |
| --- | --- | --- |
| prefill | 1024 个**输入** token | 第 1 个输出（由最后输入的 logits 算出，**此时尚未进入模型**） |
| decode #1 | 第 1 个输出（作为输入回送） | 第 2 个 |
| … | … | … |
| decode #1023 | 第 1023 个输出（回送） | **第 1024 个＝最后一个，直接返回用户，不回送、不写 KV** |

KV 记录 = 1024 输入 + 1023 回送 = **2047**。差的那个 1 正是最后返回的 token——正文 2.2.3 原话："**最后返回的 token 尚未重新送入模型，所以请求结束时并不自动为它保存 KV**"。代码依据同一条链：`generation()` 的 "G counts *subsequent model calls that **each append one KV token***"（1023 次调用各追加 1 条）＋ `qwen3.py:264` 的 `kv_final_resident_bytes = batch×(history+steps)×per_token`。已验证：把 `steps` 加到 1024（模拟下一轮对话把它回送），最终 KV 才是 2048——多轮对话里上一轮的最后输出要到**下一轮作为输入**时才写 KV。情况二同理：1151 = 1024+127。

### 追问二：batch 多大时，每步 KV 读取超过权重读取？（正文例题 2-2 的练习版）

批内共享省的是权重，但 KV 各请求独立、不能共享：每步权重读一遍 R_W ≈ 15.137 GB（实测 `Scenario(batch, history=1024, tokens=1)` 的 `weight_read_once_per_operator_bytes`，与例题 2-2 的 15,136,811,008 同源），KV 读取 = B×c_KV×H。两者相等的交点：

$$B_* = \frac{R_W}{c_{\mathrm{KV}}H} = \frac{15{,}136{,}819{,}200}{147{,}456\times H}$$

以本练习 H=1024 代入：B\* = **100.25**，即 **B=101 起每步 KV 读取超过权重读取**（实测 B=100 时 KV/权重=0.9975，B=101 时 1.0075，B=128 时 1.28）。

| 历史 H | B\* | 最小超过 batch |
| ---: | ---: | ---: |
| 1,024 | 100.25 | **101** |
| 2,048 | 50.12 | 51 |
| 4,096 | 25.06 | 26 |
| 8,192 | 12.53 | 13（例题 2-2 的答案） |
| 32,768 | 3.13 | 4 |
| 131,072 | 0.78 | 1（B=1 就已超过） |

这张表就是例题 2-2 结论"上下文越长，批内权重复用的收益就越早受到限制"的展开：B 越过 B\* 之后，decode 的带宽瓶颈从权重**转移到 KV**——再加 batch 不再省带宽，反而让每步 KV 读取线性变重。两点口径说明：①本练习的 H 在生成中从 1024 涨到 1150，B\* 相应从 101 降到 ~90（用步末 H 算即可）；②这里只算旧历史读取，每步当前 token 的 KV（B×c_KV）量级小得多。

## 3. 实验 03-01 解读：同一论断的放大版

实验保持每请求总 4,224 token 只改输入/输出占比（README 表，本地重跑一致）：

- **矩阵工作只差 7%**（A: 512.8 vs B: 548.5 TFLOPs, batch=8）——总量口径下两时段"几乎一样"；
- **decode 权重读取差 29 倍**（1,804 vs 52,329 GiB）：B 时段 3,712 步 × 每步 ~14.09 GiB，A 时段只有 128 步。读取轮数 = 输出 token 数，这就是练习"轮数"结论的 29 倍版本；
- **batch 分摊**：batch 8→32 时段 A 的 decode 权重读取一字不变（1,804.5 GiB）——与练习"8 条共享一轮"同一机制，规模更大；
- **结束 KV 只看总长**：两时段最终序列长同为 4,224 ⇒ KV 相同（0.58/4.64/18.56 GiB 随 batch）。

- 8 条不同步（输出长度 1..128 均匀分布）时，同步批的 decode 步数是多少？（128 步——由最长请求决定；总轮数不再等于 Σn_d/8，气泡来自先完成的槽位。）
