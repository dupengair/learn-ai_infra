## 2. 代码解析

### 2.1 分派直方图：`routing_counts()`（qwen3_moe.py:37-59）

```python
if policy == 'balanced':
    quotient, remainder = divmod(rows * top_k, experts)
    counts = [quotient + (e < remainder) for e in range(experts)]   # 64×8/256 → 全部=2
elif policy == 'concentrated':
    counts = [rows if e < top_k else 0 for e in range(experts)]     # 前 8 个=64，其余 0
```

这是**声明式直方图**而非真实路由（assumption："每个 MoE 层使用同一声明直方图，无 padding/token drop"）——练习问的 t_e 分布，代码就是这两行。校验 `Σcounts = m·k`（:57）保证两种分派的总分派数相同。

### 2.2 三个量分离：`add()` 的三个乘数（experts.py:62-72）

routed 行调用 `add(name, 'routed', assignments, r, f, layers, stored_copies=g['experts'], visited_copies=union)`：

- `matrix_flops` 用 `assignments`（Σt_e）⇒ **计算量 ∝ 总分派数**
- `uniform_weight_payload_bytes` 用 `union` ⇒ **读取量 ∝ 访问并集**
- `parameters` 用 `stored_copies=experts` ⇒ **容量 ∝ 专家总数**

正文"计算随 token 数线性增长，权重载荷随批内专家并集增长，而并集有上限"（实验 README 判断）的每一句都落在具体字段上。

## 3. 练习解答（全部已用代码逐位验证）

### 第一问：B=64、256 专家、top-8、一层（d=2048，f=512，SwiGLU 3 矩阵）

| 量 | 均匀分派 | 集中分派（同一组 8 个） |
| --- | ---: | ---: |
| t_e 分布 | **256 个专家各 2** | **8 个专家各 64**（248 个为 0） |
| Σt_e（总分派） | 512 | 512 |
| routed FLOPs | 512×2×3×2048×512 = **3.2212 GFLOPs** | **3.2212 GFLOPs（相同）** |
| 被访问专家数 | **256** | **8** |
| BF16 权重读取 | 256×3×2048×512×2B = **1.5 GiB** | 8×…×2B = **48 MiB** |

与正文表（1.5 GiB / 48 MiB）一致；与实验产物 `qwen36-b64-t1.json` 逐位核对：decode b64 全模型 routed = 0.128849 TFLOPs = 40 层×3.2212 GF ✓，权重读 60.0 GiB = 40×1536 MiB ✓。

**要点**：FLOPs 只看 Σt_e（每 token 的专家计算是刚性的，选哪些专家不影响做了多少乘加）；权重读取只看并集——同一份 6 MiB 的专家权重，均匀时只服务 2 个 token、集中时服务 64 个 token，**权重复用率（te）提高 32 倍，理想读取量降到 1/32**。代价是分组 GEMM 形状从"256 个 2 行小矩阵"变成"8 个 64 行矩阵"——后者其实对 kernel 更友好（正文："权重复用和计算效率因此都会受到影响"）。另注意均匀分派下 B=64 已把 256 个专家**全部点亮**，batch 再增大权重读取也停在 1.5 GiB/层——这就是实验 README"并集有上限、60 GiB 触顶"的机制。

### 第二问：E 256→128、f 512→1024、k 8→4

| 量 | 基线 | 变体 | 变化 |
| --- | ---: | ---: | --- |
| 专家总参数 3Edf | 256×3×2048×512 = 805,306,368 | 128×3×2048×1024 = 805,306,368 | **不变**（E·f 乘积不变） |
| 每 token 专家运算 6kdf | 8×6×2048×512 = 50,331,648 | 4×6×2048×1024 = 50,331,648 | **不变**（k·f 乘积不变） |
| 一层 routed FLOPs（B=64） | 3.2212 GF | 3.2212 GF（Σt_e=256×每分派翻倍） | **不变** |
| 权重读取（均匀/集中） | 1.5 GiB / 48 MiB | 1.5 GiB / 48 MiB | **不变**（单专家参数翻倍 × union 减半抵消） |
| 单专家参数 | 3,145,728 | 6,291,456 | ×2 |
| 路由器参数（∝E） | 2048×256 | 2048×128 | ×0.5 |

**答案：两者都不变**。3Edf 与 6kdf 中各有一个乘积（E·f、k·f）恰好保持——这正是"稀疏激活让总参数量与每 token 实际计算量可以分别调整"的又一面的逆命题：这三个量也可以**同时不变**地重新分配。真正变化的是矩阵形状（更少更大的专家矩阵 ⇒ 分组 GEMM 效率更高、路由器更省）与极端负载下的行为；正文 2.5.1 用 Qwen3-235B 的 128×1536×8 vs 64×3072×4 做了同型对照（`results/qwen235-granularity-baseline.md`，granularity 系列 454 GFLOPs 相同）。

### 第三问：共享专家与潜空间投影如何计入

**共享专家**（处理全部 m 个 token，不经路由）：
- 参数量：+ 层数×3×h×f_s（K3 的 f_s = n_shared×f，拼接宽度，`experts.py:84`）
- 运算量：+ 2·m·3·h·f_s（**m 是全部 token 数**，不是 Σt_e）
- 一层总式：`2mN_s + 2Σ_e t_e N_e`（正文 2.4.3）——共享项像稠密 FFN 一样线性于 m，路由项线性于 Σt_e=m·k。Qwen3.6（f_s=512）B=64 单层：2×64×3×2048×512 = 0.4027 GF，×40 层 = 16.1 GF = 实验 README 的"共享 0.016 TF" ✓。

**潜空间专家（K3，`experts.py:75-80`）**：路由分支在潜空间 r=3584 中运行，要在专家账本两侧各加一笔**全 token**执行的投影：
- 进入：`routed_expert_down_proj` [m,7168]×[7168,3584]，每个 token 都要降维（不能只投影被选中的——下一个 token 选哪些专家事先未知，且投影在路由之前）
- 离开：`routed_expert_up_proj` [m,3584]×[3584,7168]，合并后的表示升回主干
- 参数 +层×2×h×r，运算 +2·m·2×h×r；实测产物 `experts-kimi-k3-b64-balanced.json`：`latent_matrix_flops = 0.605 TF`（vs routed 6.22、shared 1.56 TF），`latent_norm_scale` 元素数另列不混入参数（assumption：矩阵字段只计 GEMM，归一化系数按元素单列）
- 对照：共享专家留在主干 7168 维（`experts.py:82-83` 注释），只有路由分支走潜空间——所以降维省的是"896 个专家×3072"那一大块，代价是进出两次全宽投影。

## 4. 实验 02-06 `run.py` 解析（141 行）

1. `qwen36_expert_rows()`（:37-70）：从 `qwen36-forward` 的逐算子账按名字前缀 `moe.router/moe.shared/moe.expert` 三分类汇总，`experts_with_work` 以 `matrix_flops>0` 判定——**逐专家列出 256 行算子**是这种账本的特色（`per_expert` 取 FLOPs 前 8 名）；

3. V4/K3 台账（:92-101）：`experts --model … --routing {balanced,concentrated}` × batch {1,64}——`--routing` 参数就是练习"两种分派"的 CLI 入口（`cli.py` experts 子命令）。

进阶自问：

- B=1 的 decode 为什么权重读只有 1.875 GiB？（1 token×top-8 ⇒ union=8 ⇒ 8×6 MiB×40 层—— routed 读取由**本批 token 数的下限 min(m·k, E)** 决定，与 batch 的关系是 sublinear。）
- B=16 时均匀分派的 union 是多少？（16×8=128 分派 ⇒ 恰好覆盖 128 个专家、每专家 1 token——`divmod` 给出的最小覆盖；B≥32 才开始出现 te=2。）
- K3 的 concentrated（union=16）与 balanced（union=896）权重载荷差多少？（产物里两者 `uniform_matrix_weight_payload_bytes` 都显示 124.46 GiB——因为该字段把 shared/dense/latent/router 也计入，路由分支只差 routed 一项；读 `expert_matrices` 逐行才能分离。这本身就是"汇总字段会掩盖结构差异"的例子。）
