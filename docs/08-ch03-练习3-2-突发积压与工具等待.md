# 练习 3-2 分析：突发请求与工具等待如何增加积压和状态占用

> 练习 3-2〔核心〕：λ_w=7,471.2 步/秒的突发持续 30 秒，decode 资源取两/三张 RTX PRO 6000 Blackwell WE（每卡 ≈2,796 步/秒），初始队列为空，求积压随时间变化与排空时间；另一种负载：2 任务/秒进入工具等待、每个等 10 秒、占 1 GiB，求稳态平均等待数与占用，等待延长到 30 秒后重算。
>
> 正文对应 `manuscripts/03-推理与训练负载.md` 例题 3-1（流体队列递推与带宽下界）、其后的突发公式（:141）、:65 的稳态占用公式 λM₀τ。

## 0. 实验与练习的对应关系

## 2. 练习解答（解析计算，公式与例题 3-1 精度一致）

### 第一部分：30 秒突发 @ 7,471.2 步/秒

**两张卡**（μ = 2×2,795.66 = 5,591.33 步/秒，λ/μ = 1.336 超载 33.6%）：

- 净积压速率 = 7,471.2 − 5,591.33 = **1,879.87 步/秒**（初始队列为空 ⇒ 无"先消化"阶段，从 t=0 起线性堆积）；
- **Q(t) = 1,879.87·t**：Q(10 s)=18,799 步，Q(20 s)=37,598 步，**Q(30 s)=56,396 步**；
- 停止到达后排空：56,396/5,591.33 = **10.09 秒**；全部工作在第 **40.09** 秒完成（30 秒到达 + 10.09 秒排空）；
- 直觉校验：积压 56,396 步 ÷ 64 并发 ≈ 881 个"请求位置"的差距——排空要按整卡速率走，与还有多少请求在等无关。

**三张卡**（μ = 3×2,795.66 = 8,386.99 步/秒 > λ = 7,471.2）：

- 利用率 ρ = 7,471.2/8,386.99 = **89.1%**，富余 915.78 步/秒；
- 初始队列为空 ⇒ **积压恒为 0，排空时间为 0**——到达的每一步工作都立即被消化；
- 这是"加一张卡"的**质变**而非量变：两卡时系统不稳定（ρ>1，积压无界增长），三卡稳定（ρ<1）。但余量并不奢侈：λ 再涨 **12.3%**（或一张卡降速 12%）就回到临界——稳态设计要留 ρ<1 的余量，因为 μ 是带宽下界、实测只会更低。

**与例题 3-1 的对照**：同样的 λ，60 秒突发积压 112,792 步、排空 20.17 秒（正文）；30 秒突发恰好减半（56,396 步、10.09 秒）——正文 :141"突发持续时间加倍，积压与排空时间都加倍"的验证。

### 第二部分：工具等待（稳态，L = λ·W）

| 等待时长 W | 平均等待任务数 L=λ·W | 状态占用 = λ·M₀·W |
| --- | ---: | ---: |
| 10 秒 | 2×10 = **20 个** | **20 GiB** |
| 30 秒 | 2×30 = **60 个** | **60 GiB** |

这就是正文 :65 公式 λM₀τ 的代入：任务流稳定后，任意时刻"正在等待"的任务平均有 λW 个——等待 10 秒的每一秒里都同时"悬浮"着此前 10 秒进入的所有任务（2/秒×10 秒=20 个），每个挂 1 GiB 状态。等待延长 3 倍，**占用线性涨 3 倍**——Agent 的工具等待由此成为容量问题：模型不计算，但 60 GiB 的 KV/上下文空间被占着（这正是章首说的"等待工具结果时模型暂停生成，上下文状态却仍要保留"，也是第 8/9 章"利用等待时间换出状态"的动机）。

## 3. 实验 03-02：真实回放的执行流程与代码

目录构成：`run.py`（69 行，回放客户端）+ `analyze.py`（52 行，审计式分析）+ `plot.py`（25 行，时间线图）+ `workloads.json`（480 条到达计划，逐项绝对时刻）/`inputs.json`（token IDs，**LFS 指针**）+ `results/arrival-v1/`（已交付完整运行：environment.json、scheduler.jsonl 采样、两 case 的 requests/dispatch.jsonl、gpu-activity.log）。

**run.py 流程**（本地无需也无法重跑，需 GPU+vLLM 0.23）：

1. `:33` 起 `AsyncLLMEngine`（engine-config.json：Qwen3-8B、24 GiB KV 池、最多 64 序列、APC 关、eager）；
2. `:34-37` 两个 case（uniform / phased）各自先 warmup（A/B 各 8 token）；
3. `:53-57` **open-loop 到达**：对 workloads.json 的每条 `arrival_s`，`sleep(origin+arrival_s−now)` 后即发（不等前一个完成、不降速）——这是回放的关键设计，"计划 4 rps"由 dispatch 记录事后核对；
4. `:46-47` 每请求 greedy + `ignore_eos=True` 固定输出长度（固定工作量，非自然结束）；记录 dispatch lag、每个流事件时刻、完整 output_ids、输入 sha256；
5. `:14-25` 自定义 StatLogger：≤10 Hz 采样 running/waiting/kv_usage，抢占事件逐次记录；
6. `:57-59` 到达窗口结束后**继续等全部完成**（排空不截断）——对应练习"停止到达后清空积压"的实测版。

**analyze.py：审计链而非统计脚本**——`assert env['status']=='passed'`、5 个输入文件 sha256 复核（:8）、480×2 完成与 index 对齐（:11-12）、逐请求输入哈希与输出长度（:20-23）、两 case 同请求输出**逐 token 一致**（:29-31，证明差异只来自时序）、最近秩 p95、10 秒 bin、两个 60 秒窗的组成断言（216/24 与 24/216，:34-37）、drain_after120、waiting/KV 峰值与抢占数。

**结论来源**：README/正文表（p95 299.4 s、TTFT 差 16 s、KV 100%、抢占 62/24）全部出自 `results/summary.json`；`timeline.svg`（plot.py 产物，在库）可视化两 case 的累计 dispatch/completed、waiting/running、KV 占用。

## 4. 实验结论与解析模型的对照

- **积压在真实系统里更糟但方向一致**：解析下界说 552,480 步 decode 至少 197.6 秒（正文 :135），实测最后完成 419.8/418.7 秒——两倍余量来自 prefill 抢带宽、KV 池 100% 触发抢占（62/24 次）、单卡（回放只有一张卡，μ 是例题两卡的一半）；
- **"平均相同、分布不同"的实证**：两 case 完成时间几乎相同（419.8 vs 418.7 s——总工作量一样），但 TTFT p95 差 16 秒（242.9 vs 258.9）——时序组成改变的是"用户何时开始看到输出"，不是"系统何时忙完"；
- **排队有两种成因**（正文 :139）：处理速率不足（流体模型刻画的）与**状态池占满**（KV 100% 时即使算力空闲也得等——练习第二部分工具等待的实证镜像：状态被占住，资源空闲也没用）。

## 6. `timeline.svg` 六图解读（plot.py 2 行 × 3 列）

布局：**行 = case**（上行 uniform、下行 phased），**列 = 视角**（累计请求 / 采样队列 / KV 占用）；每图两条竖线：t=60（灰，混合比分界）与 t=120（黑，到达窗口结束，此后进入排空段）。

**列 1：累计 dispatch（实线）与 completed（虚线），A/B 分色**——积压的直接可视化：

- uniform：A、B 的 dispatch 实线全程斜率恒定 2.00 条/s（两条平行直线），120 s 各达 240；completed 虚线在到达期内只爬到 121 条，之后以 ≈1.2 条/s 追赶，t≈419.8 s 汇合于 480；
- phased：A 的实线**前 60 s 斜率 3.60/s、后 60 s 0.40/s，B 正相反**——两条 dispatch 曲线呈"交叉"形，拐点就在 t=60 灰线处；completed 的收拢形状与 uniform 几乎一样（最后完成 418.7 vs 419.8 s）；
- **读法**：completed 与 dispatched 之间的**垂直距离 = 系统内未完成请求数**，两 case 都在 t=120 附近达最大（359/349 条）后线性收拢——这就是"总工作量相同 ⇒ 完成时间几乎相同"。

**列 2：waiting（红）与 running（蓝）采样序列**——两种排队的形状：

- uniform：waiting 从 t≈7 s 出现匀速爬升，峰值 305 @ t=118 s，排空段缓慢下降，t≈379 s 归零；running 快速上升后从 t≈48 s 起贴住 64（max_num_seqs 上限，t=200–400 均值 58.7）；
- phased：waiting **t≈0.9 s 就出现**（前 60 s 的 A 类 8192 输入 prefill 重，立刻排队），第二分钟陡增至峰值 316 @ t=120 s，t≈378 s 归零；running 从 t≈195 s 起长期贴 64（均值 61.1）；
- **读法**：waiting 曲线的形状差异（匀速爬升 vs 前慢后陡）正是 TTFT p95 差 16 秒的来源；running 贴 64 说明并发槽满——等待的成因是"槽 + KV 满"，不是算力空闲。

**列 3：KV 池占用 %**——状态池约束的时序：

- 两 case 都在 **t≈10–14 s 就首次触及 99%+**，此后长期高位徘徊（≥99% 采样 424/2883 与 247/3077——采样点非连续时长），最后一次 ≥99% 在 t≈375 s，与 waiting 归零（≈378 s）几乎同时；
- **读法**：KV 池远早于到达窗口结束就满了——从 t≈10 s 起系统就处于"状态池约束"运行：新请求等旧请求释放 KV，抢占事件（62/24 次）发生在这一段；两 case 该图几乎相同，因为 KV 总需求只由请求集合决定、与到达时序无关。

**两行合看的三个结论**：① dispatch 形状不同（平行 vs 交叉）而 completed 收拢几乎相同——时序改变用户等待、不改变系统总忙时；② waiting 形状差异量化了"时段负载"对体验的影响；③ KV 曲线相同印证约束层次：本实例的首要瓶颈是 24 GiB KV 池而非 64 并发槽（更非算力）。
