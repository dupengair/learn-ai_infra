## 3. 核心实现解析：`sequence_dependencies.py`（194 行）

### 3.1 教学模型定义（练习的"固定教学权重"）

- `D, F, L = 4, 8, 3`（:9）：宽 4、FFN 宽 8、3 层。刻意取极小，让依赖关系能用手数清。
- `matrix(rows, cols, seed)`（:13）：权重元素 = `(((i+1)*17+(j+1)*11+seed*7)%19-9)/32`。纯算术伪随机、无随机数 API、每层 seed 不同（`2+7l, 3+7l, …`），保证任何人任何时候复算出的数字逐位相同——这是"固定教学权重、FP64"的实现。
- `embedding(token, position)`（:21）：token 查表 + **加性位置信号** `(position+1)*(j+1)/64`。两个教学模型共用同一张输入表，所以后续"同一模型缓存 vs 不缓存"的对比才是严格同输入。
- `weights()`（:26）：每层 8 个矩阵。RNN 用 `wx, wh`；Transformer 用 `q, k, v, o, up, down`。参数量在 `summary` 里对账：RNN `L*2*D²=96`，Transformer `L*(4D²+2DF)=336`。

### 3.2 三种前向函数与缓存一致性检查

这是理解"缓存改变的是工作量，不是结果"的钥匙：

- `rnn_step(x, state, params)`（:33）：逐层 `h = tanh(x·wx + h_prev·wh)`，返回输出和**每层新状态** `updated`。注意它每层都依赖上一层同 token 的输出——这就是深度边。
- `transformer_full(tokens, params)`（:56）：**一次处理整个序列**。每层先给全部位置算 K/V（`keys`、`values` 两个列表），再让每个位置 `transformer_layer(x, keys[:i+1], values[:i+1], w)`——切片 `[:i+1]` 就是因果掩码的代码表达：位置 i 只能看见 ≤i 的历史。
- `transformer_step(x, cache, params)`（:64）：**逐 token 生成**。每层先把当前输入的 K/V **append 进缓存**，再用完整缓存算注意力。对应"复用状态"场景。
- `calculate()`（:136）中的检查循环：对 5 个前缀长度（1~5 个 token），分别用"逐步喂入并复用状态"（`rnn_step`/`transformer_step` 的流式结果）和"从头重算整个前缀"（`transformer_full` 等）两条路径算最后位置输出，逐元素比最大绝对误差，容差 1e-12。5 个位置 × 2 个模型 = **10 项检查**，实测最大误差 **0**（逐位相同）。

### 3.3 依赖图与最长链（练习要求 1、3）

`dependency_graph(model, tokens=4)`（:72）：

- 节点 `l{层}t{token}`，共 3×4=12 个。**不含输入 embedding 节点**（说明见字段 `input_edges`：第一层格点还会读输入 embedding，但输入在 t=0 就绪，不占链长）。
- RNN 的边（:77-79）：
  - `depth`：`l(l-1)t → llt`，共 (L-1)×T = 2×4 = 8 条——层间依赖；
  - `recurrent_state`：`l1t(t-1) → l1tt`，同层跨 token，共 L×(T-1) = 3×3 = **9 条**（README 表里的 9）——时间递推。
- Transformer 的边（:80-84）：仅当 `l>1` 时，位置 t 的格点连向**上一层全部 0..t 位置**：自己那条是 `query_and_kv`（深度依赖），其余是 `historical_kv`（读历史 KV），共 L 层中 Σ(t+1) = 2×(1+2+3+4) = **20 条**，其中 12 条 `historical_kv`（README 表里的 12）。
- 最长链（:85-89）：按"层优先、token 次之"的顺序遍历节点，父节点一定先出现（同层时 source 的 t 更小），所以一遍循环就是拓扑序 DP：

  ```
  depth(节点) = 1 + max(所有父节点的 depth)，无父则 1
  unit_node_critical_path = max(depth)
  ```

  **RNN**：`depth(l,t) = 1 + max(depth(l-1,t), depth(l,t-1))`，解得 `depth(l,t) = l+t-1`，最大 `depth(3,3) = 6`。手推关键路径：`l1t0 → l1t1 → l1t2 → l1t3 → l2t3 → l3t3`，即 4 步时间递推叠 3 层深度（重合 1 个节点）。
  **Transformer**：`depth(1,t)=1`（第一层各位置互不依赖、可同时算），`depth(2,3)=2`，`depth(3,3)=3`。12 条 `historical_kv` 边**没有一条**位于最长链上——它们连接的节点在同一"波"里可以并行计算。

### 3.4 第 5 个输出位置（练习要求 2）

- `calculate()` 里 `all_tokens = TOKENS + (4,)`（:137）：第 5 个 token 是**供给的**（`scenario.next_supplied_token=4`），不是采样出来的——避免把"采样质量"混进依赖分析（见 `assumptions` 第 4 条）。
- 对 RNN：生成位置 4 之前必须等 `l3t3`——第 4 个 token 走完 3 层后的状态。整条递推链 `l1t0→…→l3t3` 一共 6 个节点都得先算完。
- 对 Transformer（复用缓存）：`transformer_cache_graph()`（:94）专门画了缓存后逐 token 生成场景的细粒度图，输出到 `results/cache-graph.json`。注意该文件按默认 `tokens=4` 导出，只含 4 个已知 token（28 节点、54 边）；**第 5 个位置要显式调 `transformer_cache_graph(tokens=5)` 生成**（35 节点、75 边）。位置 4 的第一层格点 `l1t4` 只依赖：①`input4`（供给的 embedding，就绪即算）；②`kv1t0..kv1t3`（**前缀的 K/V 早已写好，读取不需要等待计算**）。真正的等待链只剩 `input4 → kv1t4 → l1t4 → kv2t4 → l2t4 → kv3t4 → l3t4`，长度 = L = 3 层。
- `execution_order` 字段（:109）给出了缓存复用的执行顺序约定：token 升序、层升序，每个 K/V 投影只执行一次。

### 3.5 FLOPs 与状态（README 两张表的来源）

- `matrix_rows()`（:113）：按 `flops = 2·m·k·n` 的声明式约定数矩阵乘法（`assumptions` 第 6 条明确 tanh/exp/softmax 等非线性不计入）。`rhs_kind` 区分 `weight`（权重矩阵）与 `activation`（QK/AV 注意力矩阵），`sequence_work` 按此分列——这样才看得出"缓存省掉的是注意力里对旧前缀重算的 QK/PV"（720→240，而不是 720→0）。
- 5 种 `mode`（:153-157）对应 README 工作表五行，其中 `four_tokens_state_reused` 与 `known_four_tokens` 的 FLOPs 完全相同（768 / 3552）——**一次处理已知输入本来就意味着每个状态只算一次**，"复用"相对的是"每个前缀重算一遍"（1920 / 8640）。
- 状态字节（:168-175）：RNN 每层存 D 维隐向量，`L·D·8 = 96 B` 定长；Transformer 存 K 和 V，`2·L·n·D·8`，5 token 后 960 B 且**随 n 线性增长**。这是全书后面 KV 容量、前缀缓存、PagedAttention 等问题的起点（README"状态"表）。

## 5. reproduce 报错诊断：`Source length mismatch`

**现象**：根目录运行 `python3 calculations/calc.py reproduce` 报
`calc.py: error: Source length mismatch: sources/qwen3-235b-a22b/model.safetensors.index.json`。

**原因链**（全部已验证）：

1. `reproduce.run()` 第一步是 `verify_sources()`（reproduce.py:147），它遍历 `calculations/configs/sources.lock.json` 中全部 **770 个** `status=downloaded` 的源文件，逐个调 `read_source()`。
2. `read_source()`（sources.py:17-28）先比**本地文件字节数**与 lock 记录的 `bytes`，再比 sha256。报错的是第一关。
3. 该文件本地只有 **132 字节**，内容是 Git LFS 指针：

   ```
   version https://git-lfs.github.com/spec/v1
   oid sha256:53dd34fac4a29fc7ee58fa9d92c7892ea6884431c3bd3d0dc93def7bbd0b8b78
   size 3332207
   ```

   而 lock 期望 3,332,207 字节。指针里的 `oid sha256` 与 lock 期望的哈希**完全一致**——说明文件内容本身没问题，只是 LFS 对象没有 smudge（克隆/精简仓库时未拉取 LFS 内容）。
4. 全仓扫描发现 lock 中共有 **17 个文件**处于同样的 LFS 指针状态（5 个 `model.safetensors.index.json`、11 个 NVIDIA/Ascend 白皮书 PDF、1 个论文 PDF），另外 reproduce 必读的场景清单 `calculations/scenarios/book.json`（13.4 MB）**也是** LFS 指针。也就是说：修好报错的这一个文件，下一个被校验的 LFS 文件仍会失败。

**修复方式**：

- **做练习（推荐路径）**：什么都不用做。`sequence-dependencies-book.json` 完整存在，`experiments/ch02/02-01/run.py` 已验证可直接跑通。
- **确实要跑 reproduce**：在仓库根目录执行 `git lfs install && git lfs pull`（本机 git-lfs 3.4.1 已安装），把 17 个文件 + book.json 的真实内容下载下来。注意这会拉取上百 MB 的 PDF；且 reproduce 会重算全部 1000+ 场景并按 `results/manifest.json` 里的 sha256 逐一核对结果（reproduce.py:91-144），对学习本练习没有必要。

## 6. 练习题参考答案（数值全部来自代码）

1. **依赖图**：见 `results/dependencies.svg`。RNN：12 节点、17 边（8 条深度 + 9 条时间递推）；Transformer：12 节点、20 边（8 条 query_and_kv + 12 条读历史 KV）。
2. **第 5 个位置的等待**：RNN 等待 `l3t3`（前一个 token 的第 3 层状态，递推链共 6 节点）；Transformer 复用缓存时只等 `input4`（供给的第 5 个 embedding）就绪，然后沿 `kv1t4 → l1t4 → kv2t4 → l2t4 → kv3t4 → l3t4` 走 3 层，历史 K/V 读取不构成等待。
3. **最长依赖链**（每格点 1 单位、并行充足、只处理 4 个已知输入）：RNN = **6 单位**（4 步时间递推 + 3 层深度 − 重合 1）；Transformer = **3 单位**（= 层数 L，与 token 数无关）。
4. **增加计算单元**：能缩短**资源型等待**——Transformer 同层 4 个位置的计算（12 条历史 KV 边可在前缀写好后一拍并行读）、RNN 反对角线上的并行格点；**不能缩短数据依赖**——RNN 的时间递推（`h_t = f(h_{t-1})`，第 t 步的输入就是第 t−1 步的输出，6 单位是依赖图决定的硬下界）和两类模型共同的逐层依赖（≥ L = 3 单位）。这也解释了为什么实际系统中 Transformer 能一次吃下整个 prompt（prefill 大矩阵乘），而 RNN 推理只能逐 token 串行。

## 8. 追问三则：依赖方向、第 5 位置等待、并行波的代码证据

### 8.1 怎么从 `dependency_graph` 看出"RNN 有时间依赖、Transformer 没有"

边 `(source → target)` 的语义是"**算 target 之前必须等 source 完成**"。所以看一个模型的时间依赖，就看它的边里有没有"同层、t−1 → t"这种位移。逐行看 :76-84：

```python
for node in nodes:                      # 为每个格点 (l, t) 找父节点
    l, t = node['layer'], node['token']
    if model == 'rnn':
        if l > 1: edges.append(dict(source=f'l{l-1}t{t}',  ...))   # 77 行：跨层
        if t > 0: edges.append(dict(source=f'l{l}t{t-1}',  ...))   # 78 行：同层递推
    else:
        if l > 1:                                              # 80-84 行：所有边都在这里
            for history in range(t + 1):
                edges.append(dict(source=f'l{l-1}t{history}', ...))
```

- **77 行**（`depth` 边）：只要不在第一层，就从**上一层同一位置** `l{l-1}t{t}` 连边——"第 l 层要等第 l−1 层的输出"。RNN 和 Transformer 都有，对应逐层加深；`l>1` 的判断是因为第一层的输入是 embedding（不建节点、t=0 即就绪）。
- **78 行**（`recurrent_state` 边）：**这就是 RNN 时间依赖的全部实现**。只要不是第 0 个 token，就从**同层、上一个 token** `l{l}t{t-1}` 连边。对应递推式 `h_t = tanh(x·wx + h_{t-1}·wh)` 里 `h_{t-1}·wh` 那一项——上一时刻状态是本时刻计算的直接输入。`t>0` 的边界对应零初始状态。
- **为什么 Transformer 没有**：else 分支里所有边的 source 一律是 `l{l-1}t{history}`——**全部指向上一层**，同层内 `t-1 → t` 的边一条都不存在。位置 t 虽然要"读" 0..t−1 的历史，但读的是上一层写好的 K/V（`historical_kv`），不是同层递推。实测计数：RNN 同层跨 token 边 9 条，Transformer **0 条**。
- **判别口诀**：看边的坐标位移。RNN 有 `(Δ层=0, Δtoken=−1)` 的边 ⇒ 时间必须串行；Transformer 所有边 `Δ层=−1` ⇒ 同层内各 token 在依赖图上平级，可同拍并行。

### 8.2 "第 5 个输出位置等谁"的实现位置

三处线索：

1. **"增加一个待生成位置"这个输入设定**：`calculate()` 的 `:137` `all_tokens = TOKENS + (4,)`（第 5 个位置就是这里加进来的），`:177` 导出为 `scenario.next_supplied_token=4`。
2. **RNN 等 `l3t3`**：实现在数据流上——`calculate()` `:140-142` 的流式循环里，算位置 4 时传给 `rnn_step(embedding(token,4), rs, params)` 的 `rs` 正是上一步返回的 `updated`（位置 3 的逐层状态，最深层即 `l3t3`）。依赖图视角下等价于 `dependency_graph('rnn', tokens=5)` 里 `l1t4` 的父节点 `l1t3`，回溯得整条链 `l1t0→…→l3t3`。
3. **Transformer（复用缓存）等 `input4`**：实现在 `transformer_cache_graph(tokens=5)`（:94-110）。第 5 列共 21 条边，分三类：
   - `input4 → kv1t4`、`input4 → l1t4`（`project_current_input` / `query_and_residual`）：**唯一的新信息入口**，等待从这里开始；
   - `kv1t0..kv1t3 → l1t4` 等 12 条 `read_retained_kv`：读历史缓存，**早已写好、不构成等待**；
   - `l1t4 → kv2t4 → l2t4 → kv3t4 → l3t4`：层间链，长度 L=3。
   关键行 `:99` `base = f'input{t}' if l==1 else f'l{l-1}t{t}'` 决定每个输出节点"等"的深度输入来自哪里；`boundary` 字段（:110）说明等待起点是"供给的输入"，没有从采样 token 发明的边。

### 8.3 "增加计算单元能/不能缩短哪些等待"怎么看：按 depth 分组 = 并行波

`dependency_graph` 里 `depth = 1 + max(父节点 depth)` 的定义保证：**同一 depth 的节点互不为祖先**，可以同一时间单位（同一拍）并行执行。把 12 个格点按 depth 分组，就得到一张并行执行时间表：

```
RNN:         6 拍，每拍可并行节点数 [1, 2, 3, 3, 2, 1]
  第1拍: l1t0                          第4拍: l1t3, l2t2, l3t1
  第2拍: l1t1, l2t0                    第5拍: l2t3, l3t2
  第3拍: l1t2, l2t1, l3t0              第6拍: l3t3

Transformer: 3 拍，每拍 4 个
  第1拍: l1t0..l1t3   第2拍: l2t0..l2t3   第3拍: l3t0..l3t3
```

从中直接读出三个结论：

- **RNN 的"反对角线并行"**：第 2..5 拍的分组恰好是 `l+t` 为常数的反对角线（depth(l,t)=l+t−1）。对角线内的节点之间没有任何边（边只能从 t 更小或层更浅的地方指进来），所以 2~3 个格点可同拍算——这是"加计算单元对 RNN 也有点用"的全部空间，最大并行度 = 3。
- **Transformer 的"一拍并行读"**：每拍 4 个格点。12 条 `historical_kv` 边全部从第 k 拍指向第 k+1 拍——第 2 拍的 4 个位置同时读第 1 拍写好的 4 组 K/V，读操作本身不延长任何一拍。1 个计算单元时 12 格点要 12 拍，≥4 个单元后降到 3 拍，加速 4 倍后撞上深度墙 L=3。
- **不能缩短的是什么**：贯穿首尾的"大小为 1"的瓶颈。RNN 第 1 拍只有 `l1t0`、第 6 拍只有 `l3t3`，关键路径上 depth 逐拍严格 +1——这条全串联链是数据依赖 `h_t = f(h_{t-1})` 造成的，计算单元加到再多，6 拍也是下界；两类模型共同的层间依赖则把下界钉在 L=3。

复现脚本（打印上面两张表）：

```python
import sys; sys.path.insert(0, 'src')
from infra_calc.topics import sequence_dependencies as s
for m in ('rnn', 'transformer'):
    g = s.dependency_graph(m)
    depth = {}
    for nd in g['nodes']:
        ps = [e['source'] for e in g['edges'] if e['target'] == nd['id']]
        depth[nd['id']] = 1 + max((depth[p] for p in ps), default=0)
    waves = {}
    for n, d in depth.items(): waves.setdefault(d, []).append(n)
    print(m, [len(waves[d]) for d in sorted(waves)], {d: sorted(waves[d]) for d in sorted(waves)})
```
