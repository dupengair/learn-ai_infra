## 2. 代码解析

### 2.1 反事实变体：`cache_sequence.calculate()`（topics/cache_sequence.py:24-34）

```python
for name, kv_heads in (('native_gqa', c['num_key_value_heads']),   # 8
                       ('counterfactual_mha', heads),               # 32 = Q 头数
                       ('counterfactual_mqa', 1)):
    variants.append(dict(name=name, ..., kv_heads=kv_heads,
        history_bytes_per_token=2*layers*kv_heads*d*element_bytes,       # ∝ kv_heads
        attention_flops_per_pair=4*layers*heads*d,                       # 与 kv_heads 无关
        kv_projection_parameters=2*layers*hidden*kv_heads*d, ...))       # ∝ kv_heads
```

这是"隔离单一因子"的教学设计：三个变体只动 `kv_heads`。实测三点（B/token、投影参数、每对 FLOPs）：

| 变体 | kv_heads | B/token | kv 投影参数 | 每对 QK/AV FLOPs |
| --- | ---: | ---: | ---: | ---: |
| counterfactual_mha | 32 | 589,824 | 1,207,959,552 | 589,824 |
| **native_gqa（实际）** | 8 | 147,456 | 301,989,888 | **589,824** |
| counterfactual_mqa | 1 | 18,432 | 37,748,736 | **589,824** |

前两列严格 ∝ kv_heads（32:8:1 = 589,824:147,456:18,432），第三列三行相同——**这一列就是练习第一问第三项的答案证据**：QK^T 与 AV 的矩阵工作量只由 Q 头数（32）、head_dim（128）决定，K/V 只是按组广播给 Q 头，配对数不变。

### 2.2 CSA 状态：`v4_state()`（topics/state.py:58-99）

逐层构造（43 层 = 2 window + 21 CSA + 20 HCA，`compress_ratios` 来自官方 config）：

```python
compressed = length // ratio if ratio else 0          # CSA: S//4；HCA: S//128；window: 0
indexed = compressed if ratio == 4 else 0             # 只有 CSA 维护索引
selected = min(compressed, topk) if ratio == 4 else compressed   # CSA 受 top-512 限制；HCA 全读
window_entries = min(window, length)                  # 128 定长
```

每层账目（:77-88）里的关键行：`compressed_history_bytes`（保存）、`index_scan_payload_bytes = indexed × index_width × 2B`（扫描）、`main_selected_payload_bytes = (window_entries + selected) × width × 2B`（主注意力实际读进来的）。另有 `last_query_main_qk_pv_flops = 4·batch·n_heads·width·(window_entries+selected)`（:84）——注意分母同样只含 Q 头数，与第一问呼应。

config 实测字段：head_dim=512、window=128、index_head_dim=128、**index_topk=512**、n_heads=64。

### 2.3 实验 02-04 `run.py`：CLI 驱动模式（与 02-01/02-02/02-03 的差异）

`run(args, out)`（:37-43）用 `subprocess` 调 `calc.py <子命令> --format json --output <path>`，把"统一计算项目的 CLI"当作唯一数值来源、产物与参数一并存档（`FORWARD_CASES` :29-34 显式记录每次调用的 argv）。这种模式让实验天然可复现，但也意味着 CLI 失败即实验中断——本地在 `v4-forward` 处因 LFS 指针失败（state 部分已成功重新生成）。

## 3. 练习解答（全部已用代码逐位验证）

### 第一部分：Qwen3-8B KV 头 8→4（Q 头保持 32）

| 项 | 8 头（现状） | 4 头（改后） | 变化 |
| --- | ---: | ---: | ---: |
| KV 容量 c_KV | 2×36×8×128×2 = 147,456 B/token | 2×36×4×128×2 = **73,728 B/token** | **×0.5**（8192 上下文：1.125 → 0.5625 GiB） |
| KV 投影参数（k+v，36 层） | 2×36×4096×1024 = 301,989,888 | 2×36×4096×512 = **150,994,944** | **×0.5** |
| 查询-上下文交互 QK^T+AV | 4×36×32×128 = 589,824 FLOPs/配对 | **589,824** | **×1 不变** |

三项两种命运的原因：容量与投影参数都以 `kv_heads` 为因子（每少一个 KV 头就少一份要保存/投影的 K 和 V）；交互运算量按"查询-键配对"计数，配对数 = Q 头数 × 因果位置对，K/V 的头共享只是**同一份 K/V 被一组 Q 头复用**，不减少点积次数。这正是正文 2.3.1"减少 KV 头数既改变模型可表达的注意力关系，也减少服务端必须保存和读取的状态"的量化版——省的全在访存侧，计算侧一点没省。

### 第二部分：V4-Flash CSA 层，S=8192 → 16384（压缩比 4，top-512）

单个 CSA 层（21 层同构，答案按单层给出，×21 即整模型）：

| 量 | S=8192 | S=16384 | 比例 | 代码 |
| --- | ---: | ---: | ---: | --- |
| 保存条目数 ⌊S/4⌋ | 2,048（主 KV 2 MiB + 索引 0.5 MiB） | 4,096（4 MiB + 1 MiB） | **×2** | `compressed = length//4` |
| 索引扫描条目数 | 2,048（扫描载荷 0.5 MiB） | 4,096（1 MiB） | **×2** | `indexed = compressed` |
| 选中条目上限 | min(2048, 512) = **512** | min(4096, 512) = **512** | **×1** | `selected = min(compressed, topk)` |

21 个 CSA 层合计：保存 43,008→86,016 条、扫描 43,008→86,016 条、选中上限恒 21×512=10,752 条。主注意力每步实际读取（窗口 128 + 选中 512 条 = 0.625 MiB/层）在两个长度下**一字不变**。

**三者为何不按同一比例增长**：前两者由压缩比决定——每 4 个 token 汇成 1 条，条目数天然 ∝ S，翻倍的历史就是翻倍的条目（保存的是"汇完了的账"，扫描的是"为了选出 512 条必须过一遍的目录"）；选中上限却是一个**算法超参数** top-k=512，一旦 ⌊S/4⌋ ≥ 512（即 S ≥ 2048），`min` 就把它钉死，与 S 再无关。所以"S 翻倍"在保存/扫描两侧各翻一倍，在选中侧毫无作用——这就是"稀疏访问"的确切含义，以及它的代价：**扫描不稀疏**（实验 README 判断 2："1M 时索引扫描是选中载荷的 7.6 倍"）。若把 top-k 也随长度调大，三者的分工才会改变——那时主注意力读取也随 S 增长，稀疏性就丢了。

综合两问：第一问省**容量与投影**不省交互计算（GQA）；第二问省**主注意力读取**不省扫描（top-k 常数 vs 目录线性）——两类机制都把"省"局限在依赖图的某一侧，这正是把它们分开计量的原因。

- KV 头改 4 后，练习 2-3 的三项（新增/最终容量/累计读取）变成多少？（全部 ×0.5——又一次印证"位宽减半"与"头数减半"在 KV 载荷上等价，但头数减半还额外省了投影参数与写入带宽。）
