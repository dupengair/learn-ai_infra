# 练习 2-5 分析：上下文多长时，KV 容量会超过固定状态？

> 练习 2-5〔核心〕：Qwen3.6 取固定状态 61.875 MiB、每 token 20 KiB；K3 紧凑表示递推 414 MiB、卷积 20,348,928 B、每 token 27 KiB。求两模型"随上下文增长的状态 = 固定状态"的交点长度、32K/128K 总容量；256 MiB 预算下各能存多少 token；解释预算小于固定状态时为何缩短上下文也无济于事。
>
> 正文对应 `manuscripts/02-模型架构.md` 2.3.5（混合注意力的状态构成，容量模型公式 M_state(H)=M_fixed+c_state·H）。

## 3. 练习解答（全部已用代码逐位验证）

容量模型：**M(H) = M_fixed + c·H**，交点 H\* = M_fixed/c。

| 量 | Qwen3.6 | K3（compact＋KDA） |
| --- | ---: | ---: |
| M_fixed | 64,880,640 B = **61.875 MiB** | 454,459,392 B = **433.406 MiB**（414 递推 + 19.406 卷积） |
| c（每 token） | 20,480 B = 20 KiB | 27,648 B = 27 KiB |
| **交点 H\*（增长项 = 固定项）** | 64,880,640/20,480 = **3,168** | 454,459,392/27,648 = **16,437.3 ≈ 16.4K** |
| **32K 总容量** | 735,969,280 B = **701.875 MiB**（0.685 GiB） | 1,360,429,056 B = **1,297.4 MiB**（1.267 GiB，= 实验 02-05 表） |
| **128K 总容量** | 2,749,235,200 B = **2,621.875 MiB**（2.560 GiB） | 4,078,338,048 B = **3,889.4 MiB**（3.798 GiB） |
| **256 MiB 预算可存 token** | (256MiB−61.875MiB)/20KiB = **9,939 个**（余 4,096 B） | 256 MiB − 433.4 MiB < 0 ⇒ **0 个——装不下** |

（Qwen3.6 两行与 `qwen36-capacity-b1-n{32768,131072}.json` 的三项之和逐位一致；K3 两行由 `state.calculate` 现场复算，32K 与实验产物逐位一致。）

**交点的含义**：H < H\* 时固定项主导——"保存模型运行状态"本身比"保存历史"更贵；H > H\* 时每 token 的线性项主导。Qwen3.6 的 30 个线性层只配了 32 头×128²的递推矩阵（60 MiB），交点很早（3,168）；K3 的 69 层×96 头（414 MiB）固定盘子大，交点晚（16.4K）——在 8K 上下文下 K3 的 MLA 历史（216 MiB）还不及递推状态的一半，这正是正文 2.3.5"短上下文时递推矩阵是一笔显著的固定开销"的定量版。

**256 MiB 预算**：Qwen3.6 勉强可用（固定部分就占了预算的 24%，9,939 token 也远够不到 32K）；K3 **彻底不可用**。

**为何预算 < M_fixed 时缩短上下文也无济于事**：M(H) 的下界在 H=0 处取得，值为 M_fixed——这是 `qwen36_capacity.py:83`"递推状态与卷积槽不随历史线性增长"的另一面：69×96×128×128 的关联矩阵和短卷积槽是**层结构自带的**，模型一加载、第一个 token 一处理它们就得完整存在，与历史长短无关。缩短上下文只能压缩 c·H 这一项（Qwen3.6 每省 1,000 token 才省 19.5 MiB），永远省不掉 M_fixed。对 K3 而言 (预算−M_fixed) 为负，反解 H_max 连非负解都没有——**要放下 K3 的状态，预算的准入门槛是 433.4 MiB，与愿意接受多短的上下文无关**。这也是容量筛查类工具（`qwen36_capacity` 的 `necessary_budget_fits` 字段）把固定项放在"必要预算"里的原因。
